# ADR 0006 — Row Level Security PostgreSQL multi-tenant

Stato: accettata per il primo vertical slice — 2026-11-15.

## Contesto
Le query erano filtrate da tenant_id ma l'applicazione usava il login DB amministrativo. Un nuovo repository senza filtro avrebbe esposto dati di altri tenant.

## Decisione
- Uno schema owner/migrator privilegiato, ma REST e MCP usano soltanto il ruolo peritial_app. Privilegi SELECT/INSERT/UPDATE/DELETE sulle tabelle strettamente necessari; NOSUPERUSER, NOBYPASSRLS e nessun DDL.
- Tabelle perizie e documenti con ENABLE e FORCE ROW LEVEL SECURITY; policy a livello di righe su SELECT/INSERT/UPDATE/DELETE (USING e WITH CHECK) confrontano tenant_id con il GUC peritial.tenant_id.
- Ogni operazione repository apre una transazione, imposta il tenant con la funzione SQL set_config(name, value, true) e poi esegue SQL parametrizzato nella stessa transazione. A COMMIT/ROLLBACK il GUC locale è azzerato: non permane in un connection pool.
- Il tenant applicativo arriva dal JWT con issuer/audience/firma validati, mai da parametri REST/MCP.
- Lo script 001 inizializza il ruolo come NOLOGIN; in sviluppo 002 abilita LOGIN con una password esemplificativa, mentre in produzione è richiesto provisioning fuori dal repository tramite segreto dedicato.
- Le query mantengono comunque WHERE tenant_id = @tenant come doppio controllo. Test con SQL volutamente senza filtro e tenant A/B verificano i meccanismi DB.

## Limiti, rischi e conseguenze
Il custom GUC non costituisce una barriera crittografica contro SQL injection arbitraria: un attaccante con capacità SQL potrebbe alterare set_config. Parametrizzazione, least privilege, controllo dei token, audit e policy restano obbligatori.

FORCE RLS non limita un superuser PostgreSQL o un ruolo BYPASSRLS: perciò non usare mai il login owner/migration nelle API. L'accesso legacy con account admin deve essere migrato prima del traffico di produzione.

Le migrazioni versionate, provisioning iniziale/rotazione delle credenziali su Azure e on-prem, e backup/restore sono gestiti nelle issue #6, #17 e #18. Ogni nuova tabella tenant scoped richiede una policy RLS e un test reale di cross-tenant.
